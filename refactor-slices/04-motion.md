# Slice 4: Micro-Interactions + Motion

[← Back to REFACTOR_SPEC.md](../REFACTOR_SPEC.md)

**Goal:** Add delight to the key moments: ingredient detection reveal, phase transitions, recipe appearance.

**Reference:** See [Section 3.5 — Motion principles](../REFACTOR_SPEC.md#35-motion-principles) in the main spec.

**Dependencies:** [Slice 1](01-scaffold-tailwind.md) (component structure) must be done.

## Acceptance criteria

- [x] Install `framer-motion` (or use CSS-only `@starting-style` + transitions if preferred — agent's choice)
- [x] **Phase transitions:** When moving between upload → ingredients → recipes, the outgoing view fades out (150ms) and the incoming view fades in with a slight upward slide (200ms, ease-out). Replace the current `settle`/`settleBack` keyframes.
- [x] **Ingredient chip stagger:** When detection completes (or demo mode resolves), chips animate in one at a time with 60ms stagger. Each chip: `opacity 0→1, scale 0.85→1, translateY 8px→0` over 250ms.
- [x] **Recipe card entrance:** When recipes load, the three picker cards stagger in (100ms apart) with a subtle scale-up.
- [x] **Skeleton → content crossfade:** Instead of a hard swap, the skeleton fades out (150ms) and the real content fades in (200ms) with overlap.
- [x] **Scan button loading state:** Replace the simple spinner with a progress-bar-style animation inside the button (an indeterminate stripe that sweeps left to right).
- [x] **All motion wrapped in `prefers-reduced-motion` checks** — if reduced motion is preferred, all transitions are instant.

### Implementation notes / interpreted calls

- **Chose `framer-motion`, not CSS-only.** The main spec's target stack (§0) already names Framer Motion, and two criteria — the phase-transition crossfade and the skeleton→content crossfade — need an *outgoing* element to animate out while/before an incoming one mounts. Plain CSS transitions can't express "animate then unmount" without extra JS to delay the unmount; `AnimatePresence` does this natively.
- **The app's existing global `prefers-reduced-motion` rule (`app.css`) does not cover Framer Motion.** That rule clamps CSS `animation-duration`/`transition-duration`, but Framer Motion drives values imperatively (rAF/WAAPI), not through those CSS properties. Every new Framer Motion animation site calls `useReducedMotion()` locally and forces `duration: 0` (and skips the initial transform offset) when it's true. Everything already covered by the CSS rule (existing hover/focus transitions, the reused shimmer keyframe) still gets it for free.
- **Dropped the forward/back directional distinction from the old `settle`/`settle-back` keyframes.** Criterion 2 specifies one behavior — incoming view slides *up* — not a direction-dependent one. The `direction` state and `goTo`'s second argument were dead once only one slide direction remained, so both were removed rather than kept unused.
- **Phase transition uses `AnimatePresence mode="wait"`** (sequential: exit finishes, then enter starts) — matches criterion 2's "outgoing fades out and [then] the incoming fades in" reading. The recipes-phase skeleton→content crossfade uses the default sync mode instead, since criterion 5 explicitly asks for the two to overlap. Both are commented inline since the differing modes aren't obvious from the code alone.
- **Skeleton→content overlap uses a CSS grid stack (`grid *:[grid-area:1/1]`), not `position: absolute`.** Absolutely positioning the exiting skeleton would collapse its `relative` parent to zero height (an absolutely-positioned box doesn't contribute to the parent's layout size), which is wrong for the common case where the skeleton is the *only* child and hasn't started exiting yet. Stacking both children in the same grid cell sizes the container to the taller of the two, with no absolute-positioning edge case.
- **Ingredient chip stagger only applies to the initially-detected batch.** `IngredientEditor` captures `items.length` in a `useRef` on first render (the moment detection/demo mode hands it the batch) and only chips within that count get an index-based delay; chips added later via the manual-add form get `staggerIndex={0}` so a single new chip appears immediately instead of queueing behind `(list length) × 60ms` of artificial delay. Existing chips don't replay their entrance when a sibling is added/removed — React only mounts the genuinely new `<Chip>` for a new key, which is exactly the desired behavior.
- **Followed the slice's 60ms stagger, not the main spec §3.5's 50ms** — same "slice overrides the general principle" precedent used for the mono/sans call in [Slice 3](03-hero-techshowcase.md).
- **Recipe card entrance animates the `<button>` itself (converted to `motion.button`), not an extra wrapper div.** A wrapper would need to be a non-`contents` box to host a transform, which would need explicit `w-full h-full` plumbing to keep the existing CSS Grid `stretch` sizing intact — an extra layout indirection with no benefit over animating the button directly.
- **Moved the recipe card's hover-lift from Tailwind (`hover:-translate-y-0.5`) to a Framer Motion `whileHover`.** Once Framer Motion owns the `transform` on an element (for the entrance animation), a competing Tailwind `transition-transform` hover class would silently lose to Framer's inline style. Consolidating both the entrance and the hover-lift under Framer Motion avoids two engines fighting over the same CSS property. The plain color hover (`hover:bg-sunken`) stays as a Tailwind class since it doesn't touch `transform`.
- **Scan button reuses the existing `shimmer` keyframe** (already used by skeleton loading blocks) for its indeterminate sweep, rather than adding a near-duplicate keyframe — `shimmer`'s one-directional, repeating `translateX(-100%→ 100%)` is exactly "a stripe that sweeps left to right."
- **Removed the separate sweeping-stripe status row below the scan button** (it used the old `scan` keyframe, which bounced back and forth via `alternate` — not a left-to-right sweep, and a second, different-looking indeterminate indicator competing with the new one inside the button for the same loading state). Kept the "Reading your photo…" status text; the button itself now carries the sole loading affordance. The now-unused `scan`/`--animate-scan` keyframe was deleted from `app.css`.
- **Only the scan button's spinner was replaced.** Criterion 6 names the scan button specifically; `IngredientEditor`'s "Get recipes" button still uses the plain `Spinner` component — left untouched as out of scope for this criterion.

**Verification caveat**: no Chrome browser extension was connected this session — `list_connected_browsers` returned an empty list (not just a connection error, as in Slices 2–3). Verified via `npm run build`/`npm run lint` (both clean) and a dev-server request to every edited file to confirm each transforms without a Vite/esbuild error. **This is weaker verification than prior slices.** Build and lint prove the code compiles; they prove *nothing* about whether a transition's timing, easing, stagger interval, or crossfade overlap actually looks right, or whether `prefers-reduced-motion` truly makes everything instant in a real browser. This slice cannot be confirmed without a human watching it run — please exercise `npm run dev` + `?demo=1` end to end (upload → ingredients → recipes) with reduced-motion off and on (OS-level "Reduce motion" setting) before merging.

### Review-driven fixes

A two-axis code review against `3cf72ff...44de829` found no missing/wrong spec requirements and no scope creep. It caught two real issues, both fixed:

- **`RecipePicker`'s hover-lift removed the interaction entirely under reduced motion instead of making it instant.** Every other new animation in this diff honors criterion 7 by zeroing `duration`/`delay`, but the migrated hover-lift (`whileHover={!selected && !prefersReducedMotion ? {...} : undefined}`) dropped the hover feedback altogether for reduced-motion users — "absent" isn't "instant." Fixed by gating only on `!selected` and routing the transition through the new shared `reducedTransition()` helper (below), so a reduced-motion user still gets the lift/shadow feedback, just with zero duration, consistent with every other site.
- **The `prefersReducedMotion ? 0 : X` duration/delay ternary was duplicated across 4 files** (Duplicated Code) — the exact inconsistency that caused the bug above. Extracted into `fe/src/lib/motion.js`'s `reducedTransition(prefersReducedMotion, transition)`, used at every Framer Motion transition site (`Chip`, `RecipePicker`'s entrance and hover, the phase transition, and the skeleton/content crossfade).
- **`Chip`'s `staggerIndex={0}` was overloaded** to mean both "first chip in the detected batch" and "skip the stagger" (a Primitive Obsession/Mysterious Name judgement call) — a manually-added chip and the first detected chip were indistinguishable at the call site. Changed the "skip" case to pass `staggerIndex={null}` instead of `0`, with `Chip` treating `null` explicitly as "no delay" rather than relying on the numeric coincidence that `0 * 0.06 === 0`.

Left unfixed (judgement call, not urgent): the exact motion durations/delays (`0.25`, `0.2`, `0.15`, `0.06`, `0.1`) are bare numeric literals rather than named constants, unlike the old CSS custom properties they replaced. Each value is specific to a single acceptance criterion (chip stagger interval, phase-exit duration, card-stagger interval, etc.) rather than a shared design-system token like Slice 2's `tracking-tight` — extracting constants for values that only coincidentally match today (e.g. both the chip and card entrance use `0.25`) risks a false shared abstraction if a criterion's number changes later.

One reviewer note was checked and confirmed **not** an issue: `IngredientEditor`'s `useRef(items.length).current` capturing the detected-batch size on first render depends on `items` already holding the full batch by the time `IngredientEditor` mounts. In `WorkflowPage.handleScan`, `setItems(result)` and `goTo('ingredients')` (which calls `setPhase`) run synchronously in the same function body, so React batches them into one render — `IngredientEditor`'s first render already sees the full `items` array, not an empty one.
